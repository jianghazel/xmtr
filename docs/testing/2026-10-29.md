# Boundary and legacy-system testing — 2026-10-29

Three independently reproducible defects have fixes submitted upstream. The published musl binaries
also completed loopback traces on Linux 2.6.32 and 3.2. The published GNU x86_64 binary requires
glibc 2.28 and fails to start in the three older GNU userspaces tested below.

The source baseline is `Alice39s/xmtr@ead8621d7e99234cd09cac7890a91ed524256f88`.
The combined tested source is `jianghazel/xmtr@1e6fc985a881743f04e5e26cb88c7c1e54d7967a`.
This report and the VM reproduction helpers live on `audit/report`; the three upstream PRs contain
only their respective fixes and regression tests.

## Submitted fixes

| Defect | Reproduction evidence | Issue | PR |
| --- | --- | --- | --- |
| Large accepted durations overflow the conversion to `usize`; debug builds panic and release builds can stop after one round | [Failing regression](evidence/duration-before.log); published binaries return `rounds: 1`, fixed build returns `rounds: 5` in both old kernels | [#2](https://github.com/Alice39s/xmtr/issues/2) | [#5](https://github.com/Alice39s/xmtr/pull/5) |
| An IPv6 gateway with custom DNS passes `[::1]` to DNS as a name | [Failing regression](evidence/ipv6-before.log); fixed test builds both IPv4 and IPv6 agents without a DNS request | [#3](https://github.com/Alice39s/xmtr/issues/3) | [#6](https://github.com/Alice39s/xmtr/pull/6) |
| Release extraction bounds the download but leaves the executable's decompressed buffer unbounded | [Failing regression](evidence/extraction-before.log); valid compressed fixture smaller than 1 MiB expands to 64 MiB + 1 | [#4](https://github.com/Alice39s/xmtr/issues/4) | [#7](https://github.com/Alice39s/xmtr/pull/7) |

Each PR targets upstream `main`, contains one commit and changes one file. None depends on another PR.
The extraction fix checks the executable entry's declared size and bounds the reader. It does not
place a total decompression or CPU budget on unrelated archive entries.

The macOS `macos-latest` jobs remained queued; macOS 15 Intel was tested separately. The legacy GNU
jobs intentionally retain their observed startup failures in the run record. The workflow as a whole
is therefore not an all-platform pass.

`scripts/stress/cli.py` uses random seed `391029`. Its cases cover numeric limits, invalid durations,
PINs, resolver schemes, malformed Unicode input, 10,000 arguments, 8/16/32 file descriptors, and
32/64/128 MiB address-space limits for help. With `--trace`, it also checks 64 loopback routes at
parallelism 1/8/64, huge time limits, and tracing with 16/32 file descriptors. Resource-limited traces
may return a normal error; crashes and panics fail the check. Every trace uses `--no-upload` and
`--no-rdns`.

Local CLI validation completed 2,045 cases with zero failures. Raw-socket privileges are unavailable
in the local host container, so privileged source traces ran in Actions and in isolated VMs.

```sh
cargo fmt --all --check
cargo clippy --workspace --all-targets --locked -- -D warnings
cargo test --workspace --locked
cargo test --locked stress:: -- --ignored --nocapture --test-threads=1
cargo build --locked
python3 scripts/stress/cli.py target/debug/xmtr --cases 2000 --output target/stress/local.json
sudo python3 scripts/stress/cli.py target/debug/xmtr --cases 2000 --trace --output target/stress/trace.json
```

## Old kernels and CPU models

QEMU 8.2.2 ran full-system VMs with TCG, two emulated CPUs, no network device and no swap. Loopback
was enabled inside each guest. These tests boot the actual old kernels; they do not substitute an
old userspace on the host kernel.

| Kernel / memory | Binary | Result |
| --- | --- | --- |
| Debian Linux 2.6.32-5-amd64 / 64 MiB | Published 0.3.0 i686 and x86_64 musl | Version and single loopback trace pass; huge duration stops after one round |
| Debian Linux 3.2.0-4-amd64 / 128 MiB | Published 0.3.0 i686 and x86_64 musl | Version and single loopback trace pass; huge duration stops after one round |
| Linux 2.6.32 / 256 MiB | Combined fixed source, x86_64 musl debug build | Version, loopback, huge duration with five rounds and eight parallel traces pass |
| Linux 3.2 / 256 MiB | Combined fixed source, x86_64 musl debug build | Version, loopback, huge duration with five rounds and eight parallel traces pass |

Published i686 runs with 64 concurrent one-round traces produced nine unanswered routes in the 64 MiB
guest and 14 in the 128 MiB guest. Published x86_64 runs completed the same workload without reported
unanswered routes. All these processes exited normally. This does not establish the cause of the
unanswered probes or promise loss-free tracing at that load.

QEMU user-mode startup checks on the published binaries passed for x86_64 `qemu64` and `Conroe`, and
for i686 `pentium3`. i686 `pentium2` and `pentium` stopped with an illegal instruction. These are
startup-only CPU checks, not evidence that every code path supports those processors.

## Old userspaces

These Actions containers share the modern runner kernel. The downloaded 0.3.0 fixtures are verified
against the release's `SHA256SUMS` before execution.

| Userspace | Published binary | Result |
| --- | --- | --- |
| CentOS 7 | x86_64 GNU | Loader rejects missing glibc symbol versions |
| Debian Jessie | x86_64 GNU | Loader rejects `GLIBC_2.25`, `GLIBC_2.27` and `GLIBC_2.28` |
| Ubuntu 14.04 | x86_64 GNU | Loader rejects missing glibc symbol versions |
| Alpine 3.5 | x86_64 musl, static | Version and loopback trace pass |

`readelf --version-info` on the published GNU x86_64 executable confirms a maximum required symbol
version of `GLIBC_2.28`. The build uses cargo-zigbuild without an explicit glibc suffix. No lower
glibc support promise was found in the README, so this is recorded as a compatibility limit rather
than another confirmed defect. On x86_64, the standard Linux installer already selects musl binaries.

## Reproducing the VMs

The test environment uses these Debian archive fixtures:

| Fixture | SHA-256 |
| --- | --- |
| [Linux 2.6.32 package](https://archive.debian.org/debian/pool/main/l/linux-2.6/linux-image-2.6.32-5-amd64_2.6.32-48squeeze20_amd64.deb) | `d4fbb4f0d3e2dd8b5e182c72aad36079f3975679be0b1620ae0529d4ee8d4c10` |
| [Linux 3.2 package](https://archive.debian.org/debian-security/pool/updates/main/l/linux/linux-image-3.2.0-4-amd64_3.2.96-2_amd64.deb) | `7d406f0b70c1083bae428fd5396c58b28be7cab3321cb9262a1b74f2eb26b4e1` |
| [BusyBox static package](https://archive.debian.org/debian/pool/main/b/busybox/busybox-static_1.17.1-8+deb6u11_amd64.deb) | `02d9e424fb7a62c03acb16675c1244e1ef12cd6b086f1f27d570a4869ac60c35` |

1. Extract the packages with `dpkg-deb -x`. Create a root directory containing `bin/busybox`,
   `dev`, `proc`, `sys` and `etc`; put `nameserver 127.0.0.1` in `etc/resolv.conf`.
2. Put the verified musl binaries at `xmtr32` and `xmtr64` in that root. Copy
   `scripts/stress/vm_init.sh` to `init`.
3. Build the guest entropy helper. It uses Linux x86_64 system calls and has no libc requirement:

   ```sh
   gcc -Wall -Wextra -Werror -nostdlib -static -fno-stack-protector -fno-pie -no-pie \
     scripts/stress/vm_seed.c -o target/vm-root/seed-entropy
   uv run --with libarchive-c python scripts/stress/vm_archive.py \
     target/vm-root target/initramfs.cpio.gz
   ```

   The archive helper generates a fresh random seed and device entries. The guest credits that
   seed to its entropy pool, needed before old-kernel Rust randomness can initialize. No seed is
   committed. The helper is intended to run inside the test VM.
4. Boot with the extracted kernel. The tested command uses `-m 64` or `-m 128` for published binaries:

   ```sh
   timeout 55 qemu-system-x86_64 -accel tcg -cpu qemu64 -smp 2 -m 128 \
     -kernel target/kernel/boot/vmlinuz-3.2.0-4-amd64 \
     -initrd target/initramfs.cpio.gz \
     -append 'console=ttyS0 rdinit=/init panic=-1' \
     -nographic -no-reboot -nic none -vga none
   ```

For the combined fixed-source observation, the x86_64 musl debug executable was built with
`cargo zigbuild --locked --target x86_64-unknown-linux-musl` using Zig 0.14.1. It was stripped of debug
sections and tested with 256 MiB, one binary and eight concurrent routes. The report does not compare
its memory consumption directly with the optimized published binaries.
